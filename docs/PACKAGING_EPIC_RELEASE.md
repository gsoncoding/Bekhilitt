# Упаковка и повторная сборка Epic-релиза

Это инструкция для `scripts/package-epic-release.py`. Она описывает проверяемую
упаковку уже подготовленного кандидата и **не утверждает**, что игровой QA
пройден. Результаты, ограничения и hash проверенного JAR находятся в отдельном
QA-документе конкретного выпуска. Скрипт не запускает игру, не собирает код,
не скачивает зависимости, не принимает EULA и ничего не публикует.

## Состав одного пользовательского ZIP

Внешняя папка `Bekhilitt-<версия>/` содержит:

- `mods/bekhilitt-<версия>.jar` — единственный игровой JAR, собственный мод;
- `Bekhilitt-<версия>-source.zip` — полные собственные исходники;
- `DEPENDENCIES.json`, `scripts/fetch-official-mods.py` и его offline-тесты;
- `README.md`, `CHANGELOG.md`, русские инструкции, QA и описание выпуска в `docs/`;
- `scripts/package-epic-release.py` для проверки полученного архива;
- `FILES.json` — все остальные файлы внешнего ZIP, их размер и SHA-256;
- только явно выбранные native Minecraft PNG в `screenshots/`, если они были
  переданы упаковщику. Точный список находится в поле `screenshots` у `FILES.json`.

Во вложенном source ZIP корневая папка называется `Bekhilitt-source/`. В ней
лежат `src/` с Java-кодом, собственными ресурсами и Java-тестами, Gradle config и
wrapper, `DEPENDENCIES.json`, документы, генераторы собственной графики,
переносимый `scripts/dev.sh`, загрузчик зависимостей и Python-тесты. Файл
`SOURCE_FILES.json` содержит SHA-256 и размеры остальных файлов исходников.

Индексы не хешируют сами себя: source index защищён hash всего source ZIP во
внешнем индексе; hash внешнего ZIP нужно сравнивать с независимым сообщением
поставщика. Это контроль целостности, **не цифровая подпись** и не доказательство
происхождения неизвестного пакета.

Epic Fight, Terralith, Explorify, Minecraft и NeoForge не вложены ни как JAR,
ни как скопированные assets/исходники. Из исходников исключены игровые папки,
миры и save fixtures, локальные библиотеки, build/cache/JDK, Git и облачные
launch-скрипты. Исторический launcher 1.1.0 также не входит. Единственное
исключение для стороннего бинарного файла — официальный Gradle wrapper 9.2.1,
который является инструментом сборки. Его SHA-256 и SHA-256 Gradle distribution
закреплены и сверены с [официальной страницей Gradle](https://gradle.org/release-checksums/).

## Пользователь: сборка из вложенных исходников

1. Распакуйте source ZIP и перейдите именно в `Bekhilitt-source`, где находятся
   `build.gradle`, `gradlew`, `scripts/` и `DEPENDENCIES.json`.
2. Используйте полный JDK 21 и Python 3.9+. Убедитесь, что `java -version` и
   `javac -version` относятся к JDK 21; при необходимости выберите его через
   `JAVA_HOME` в текущей оболочке.
3. Получите только обязательный Epic Fight в **папку `libs` этих исходников**:

   ```sh
   python3 scripts/fetch-official-mods.py --mods-dir libs
   python3 scripts/fetch-official-mods.py --mods-dir libs --verify-only
   ```

   Manifest находится уровнем выше `scripts`; загрузчик находит его относительно
   собственного файла, независимо от текущей рабочей папки. Значение `--mods-dir`
   относительное к рабочей папке, поэтому сначала выполните шаг 1. Не передавайте
   `--include-worldgen` для компиляции: дополнительные генераторы мира для неё
   не нужны. Не добавляйте в `libs` произвольные JAR, поскольку Gradle подключает
   все JAR этой папки.
4. Если официальный download endpoint недоступен, используйте закреплённую
   страницу автора из manifest, сохраните точный JAR в `libs` с указанным именем
   и повторите `--verify-only`. Подробности безопасного отказа описаны в
   [инструкции установки](INSTALL_EPIC_PROFILE.md). До успешной проверки не
   продолжайте. Пакет не включает копию зависимости и не обещает обход блокировок.
5. Запустите сборку и локальные тесты:

   ```sh
   ./gradlew clean test build --console=plain
   python3 -m unittest discover -s scripts -p 'test_*.py' -v
   ```

   На Windows используйте `gradlew.bat` и `py -3` вместо `./gradlew` и `python3`.
   Если распаковщик на Linux/macOS не сохранил executable bit, используйте
   `sh gradlew clean test build --console=plain`.
6. Gradle самостоятельно получает свои обычные build-зависимости через
   закреплённую конфигурацию. Сеть нужна для первоначального заполнения кэша.
   Обычный runtime JAR появляется в `build/libs`; `-sources.jar` запускать как мод
   нельзя. Для игрового запуска используйте отдельный профиль по инструкции.

Готовые оригинальные PNG/JSON уже находятся в `src/main/resources`: Pillow
**не нужен** для обычной Java-сборки. Три `scripts/generate-*.py` нужны только
для изменения/повторного создания авторской графики и требуют отдельно
установленного Python-пакета Pillow. Генераторы не читают внешние изображения.

Закрепление зависимостей и полный исходный проект позволяют повторить сборку.
Битовое совпадение повторно скомпилированного JAR между различными системами и
версиями инструментов этой инструкцией не обещается. Детерминированность ниже
относится к ZIP-упаковке **одних и тех же входных байтов**.

## Подготовка релиза: сначала проверка, потом упаковка

Нужны три существующих русских Markdown-документа внутри `docs/`: инструкция,
QA и описание выпуска. Их пути задаются явно; имена в примере ниже являются
примером параметров, а не указанием создать документы с выдуманными результатами.
QA должен содержать точный SHA-256 утверждённого runtime JAR. Скрипт не вычисляет
значение параметра согласования вместо ответственного за релиз.

После завершения сборки и QA установите `APPROVED_SHA256` в уже проверенный
64-символьный hash. Сначала выполните только проверку входов:

```sh
python3 scripts/package-epic-release.py check \
  --jar build/libs/bekhilitt-1.2.0-epic.1.jar \
  --jar-sha256 "$APPROVED_SHA256" \
  --install-doc docs/INSTALL_EPIC_PROFILE.md \
  --qa-doc docs/QA_EPIC_RELEASE.md \
  --release-doc docs/RELEASE_EPIC.md
```

`check` не создаёт архив. Он проверяет точное имя и hash runtime, его namespace,
соответствие исходным ресурсам, отсутствие лишних/устаревших классов без Java
исходника, version, wrapper и обязательные файлы. Это **не заменяет** компиляцию,
QA или проверку того, что bytecode был собран из данной версии Java-кода.
Перед финальной упаковкой остановите любые изменения исходников и документов.

Только после утверждения кандидата выполните тот же вызов с `build` вместо
`check` и добавьте путь **нового** ZIP:

```sh
python3 scripts/package-epic-release.py build \
  --jar build/libs/bekhilitt-1.2.0-epic.1.jar \
  --jar-sha256 "$APPROVED_SHA256" \
  --install-doc docs/INSTALL_EPIC_PROFILE.md \
  --qa-doc docs/QA_EPIC_RELEASE.md \
  --release-doc docs/RELEASE_EPIC.md \
  --output ../Bekhilitt-1.2.0-epic.1-release.zip
```

При другой версии используйте её фактические имена файлов; version читается из
`gradle.properties`. Отдельно можно повторить `--screenshot путь/к/файлу.png`
для каждого лично проверенного native-скриншота. Автоматического захвата всех
картинок, репортов, логов или сохранений нет. PNG-сигнатура проверяется, но
упаковщик не способен доказать происхождение изображения или достоверность QA.

Скрипт проверяет ZIP до записи и повторно после записи, затем печатает его имя,
размер и SHA-256. Он фиксирует порядок записей, timestamp, Unix modes и использует
ZIP без сжатия, чтобы результат не зависел от версии zlib, времени файлов или
их исходных прав. Существующий выходной файл никогда не перезаписывается.
Один входной файл и весь готовый внешний ZIP ограничены 64 MiB; превышение
проверяется до записи итогового файла.
На файловой системе без atomic hard-link поддержки запись завершится безопасным
отказом: выберите обычную локальную файловую систему. Новая папка назначения
должна уже существовать. Символьные ссылки и небезопасные пути отклоняются.

Проверка готового архива, в том числе после передачи:

```sh
python3 scripts/package-epic-release.py verify \
  --archive ../Bekhilitt-1.2.0-epic.1-release.zip \
  --jar-sha256 "$APPROVED_SHA256"
```

Проверяются CRC, полное покрытие обоих SHA-256 inventories, сам runtime JAR,
source ZIP, запрещённые namespaces и копии manifest/helper/docs. Никакие
архивные файлы при этом не извлекаются и не исполняются. Проверку источника
пакета и сверку **самого проверяющего скрипта** нельзя заменить запуском скрипта
из неизвестного ZIP.

## Что подтверждают автоматические тесты

`python3 -m unittest discover -s scripts -p 'test_package_epic_release.py' -v`
использует только явно тестовые временные fixtures. Проверяются воспроизводимость,
полнота исходников, исключения, неправильный JAR/hash/version, несовпадающие
ресурсы, отдельные пользовательские документы, wrapper, path traversal,
symlinks, повреждение вложенного source ZIP, запрет перезаписи и явный выбор PNG.
Отдельный integration fixture запускает настоящий dependency helper в обеих
раскладках из чужой рабочей папки с `--verify-only`: сначала зависимость отсутствует,
затем тестовый файл совпадает с тестовым manifest. Сетевых запросов нет. Это не
проверка доступности хостов на компьютере пользователя и не игровой QA.
